# Model Trainer

Model Trainer has separate sub-tabs for **AlexNet**, **Transformer**, **PriceAI**,
**Agentic AI**, **Spot HGB** and **Spot LightGBM**. Each sub-tab retains its own
settings and displays its own runs and saved models. Only one run can be active
per account; cancellation remains available when viewing another family.

AlexNet and Transformer require PyTorch and can train on CUDA or CPU. The other
families train on CPU without PyTorch. Missing LightGBM disables its training
button with installation guidance; the other sub-tabs remain usable.

## Transformer: 100 observed candles, 10 future candles

The Transformer reads exactly **100 consecutive completed OHLCV candles** and
generates the next **10 full OHLCV candles one by one**. Its encoder retains the
observed history; its causally masked decoder uses earlier generated candles to
produce the next candle. It predicts opening gaps, bodies, positive wick lengths
and transformed volume, reconstructing positive prices, valid high/low bounds
and nonnegative volume. One preceding raw candle supplies the first previous
close, so prediction fetches a little more than the displayed 100 candles.
Daily candles retain Nobitex's Tehran-midnight opening times.

Defaults are 10,000 history candles, 30 epochs, batches of 16 and a learning rate
of 0.0003. A compact two-layer encoder and two-layer decoder use 64-dimensional
embeddings and four attention heads. Start with CPU or CUDA according to the
server hardware. History must cover enough consecutive examples in all three
chronological partitions.

Training uses shifted teacher forcing and standardized Huber loss. Validation
and test predictions recursively use the model's own earlier predictions for
all ten steps. The best recursive validation checkpoint is retained. All ten
future labels remain inside their partition, normalization uses training data
only, and windows spanning candle gaps are excluded. Metrics include errors by
forecast step, volume error and directional accuracy, alongside persistence
baselines. Preview displays the 100 actual candles and ten distinct forecast
candles with volume and a numeric OHLCV table. Requesting another preview reads
the latest completed history again.

Transformer checkpoints currently support training and previews. Saved model
assignment to an AI bot is available for validated compatible AlexNet models.

## Other learned models

- **PriceAI:** the existing HistGradientBoosting return predictor, with a fixed
  four-candle horizon on 1h or 4h candles and an untouched later test period.
- **Agentic AI:** calibrated classifier specialists across two or three
  timeframes. Choose one 1h or 4h primary timeframe, include it among specialists,
  and set positive entry/exit fee and slippage assumptions. Preview shows
  directional probabilities and specialist evidence. Calibration, validation
  and held-out test blocks are chronological.
- **Spot HGB / Spot LightGBM:** the existing hourly portfolio feature pipeline
  with BTC context and separate return/downside estimators at 4, 24 and 72 hours.
  Markets must belong to the supported portfolio universe. Trainer checkpoints
  are research previews; existing portfolio research remains available.

These CPU checkpoints are generated by the server and stored privately as
`.joblib` artifacts. Neural checkpoints use `.pt`. The registry determines
architecture and artifact path; clients never provide file paths.

## AlexNet and saved-model AI bots

Open **Model Trainer** beside **AI Bots**. Select USDT markets, one or more
timeframes (15 minutes, 1 hour, 4 hours or 1 day), history length, lookback and
forecast horizon. A horizon of four means the close four candles after the input
window; it represents four hours on 1-hour data and sixteen hours on 4-hour data.
The default is 2,000 historical candles, a 96-candle input, a four-candle horizon,
10 epochs and batches of 32. A run trains one independent model per selected
market/timeframe combination, with at most 12 combinations in one run.

Training uses completed **Nobitex** OHLCV candles. It runs in a background worker;
the dashboard continues to respond. The tab reports actual device availability,
progress, training and validation losses, errors and cancellation. Training jobs
are serialized across accounts so one GPU is not oversubscribed. Cancelling is
checked during queued work, historical-data pagination and training batches.
Previously completed models remain available when a later pair fails or a run
is cancelled. An interrupted run becomes `interrupted` after a server restart;
it never silently resumes.

The loss chart plots actual epoch numbers on the x-axis and mean squared error
of standardized log returns on the y-axis (dimensionless). Both curves share a
linear scale starting at zero, with numeric ticks and grid lines. Training is
solid and validation is dashed; hover a point for its epoch and loss. Missing
measurements remain gaps instead of appearing as zero.

## CUDA setup on Windows

Use the same Python environment that launches the server:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-training.txt
.\.venv\Scripts\python.exe -c "import torch; print(torch.__version__); print(torch.cuda.is_available())"
```

Restart the dashboard after installation. The optional file pins CUDA 12.8
PyTorch 2.7.1. It does not require torchvision, pretrained ImageNet weights or
a separate CUDA toolkit. A compatible NVIDIA driver is required. Check the
[official PyTorch installer](https://pytorch.org/get-started/locally/) for other
GPU, driver and operating-system combinations. If CUDA is selected and unavailable,
training fails with a setup message instead of silently running on CPU.
Select **CPU** explicitly to use a CPU installation:

```powershell
.\.venv\Scripts\python.exe -m pip install torch==2.7.1 --index-url https://download.pytorch.org/whl/cpu
```

The 4 GB RTX 3050 Ti can start with the default batch of 32. Reduce the batch to
8 or 16 if other applications consume GPU memory. An out-of-memory error is
reported in the run; no partially trained model is registered.

## CUDA in Docker

The standard dashboard image remains usable without PyTorch. On a host with
NVIDIA GPU container support (NVIDIA Container Toolkit on Linux or the supported
Docker Desktop/WSL2 NVIDIA GPU configuration on Windows), run:

```powershell
docker compose -f compose.yaml -f compose.cuda.yaml up --build -d
```

The override builds the optional CUDA runtime and exposes the GPU to the server.
The existing data volume holds the model files. GPU availability refers to the
**server**, so opening the dashboard on a GPU-equipped browser computer does not
give a remote server access to that GPU.

If the trainer says PyTorch is missing while `import torch` works in Windows,
check the **Training hardware** panel's environment and Python executable. The
standard Docker image does not include PyTorch and cannot use packages installed
in Windows Python or another virtual environment. Use the CUDA Compose command
above to install PyTorch inside the image and expose the NVIDIA GPU. Continue to
include both Compose files when rebuilding the CUDA dashboard; rebuilding with
only `compose.yaml` selects the standard image again. Building only the image
does not update an already running container.

The runtime panel distinguishes a missing package from a package that fails to
load, and preserves the import or native-library error for diagnosis. A failed
CUDA check leaves CPU training available when PyTorch itself loads successfully.

## Architecture and evaluation

`alexnet1d-v1` is an **AlexNet-inspired time-series regression adaptation**. Five
1D convolutional layers analyze normalized OHLCV windows, followed by a compact
regression head. This retains AlexNet's convolutional pattern while handling
time series and fitting a small GPU. It is not the original ImageNet image
classifier. Models learn a future log return and convert it into an estimated
USDT price from the latest completed close.

The data is split chronologically into 70% training, 15% validation and 15% test.
Training labels cannot reach into validation, and validation labels cannot reach
into test. Scaling is fitted only on training data. The best validation epoch is
saved; test data does not select weights or eligibility. Windows crossing missing
candles are excluded. Invalid OHLCV or insufficient consecutive history produces
an error instead of a fabricated forecast.

Validation and test error are reported in basis points alongside an unchanged-price
forecast. `validation_passed` requires beating that baseline on validation data.
Test metrics are diagnostics for the selected checkpoint. A baseline failure
still saves a model for inspection and price previews, but it cannot be assigned
to a trading bot. Prediction error and trading profitability are different
measurements; the saved model provides an estimate, not a guaranteed price.

## Use a saved model

Choose **Use in AI Bot** on an eligible saved model, or create an **AlexNet** bot
in AI Bots and select its compatible checkpoint. The coin and timeframe must
match. Configure positive fee, exit-fee and slippage assumptions in Research
settings. Bots are created stopped and require an explicit Start.

AlexNet bots initially support **simulation**. They use fixed saved weights,
cost-aware price forecasts and the existing next-open execution simulator.
Backtests evaluate from the checkpoint's held-out test window, excluding all
fitting and validation candles. There is no automatic retraining or automatic
start after a restart. Saved model IDs survive bot edits, duplication and restart.

Training jobs and model metadata live in the account's SQLite store. Checkpoints
live in its sibling `models` directory (`.runtime/models` in local mode,
`/data/users/<user-id>/models` in multi-user Docker mode). Back up the complete
data directory, including these files. Model IDs and account-scoped registries
prevent clients from selecting arbitrary filesystem paths or another account's
model. Checkpoints are loaded on CPU for inference using PyTorch's restricted
weights-only loader; GPU availability is required only for CUDA training.

## API

| Endpoint | Purpose |
| --- | --- |
| `GET /api/model-trainer/config` | Runtime and supported trainer settings |
| `POST /api/model-trainer/run` | Start a private training job; returns `job_id` |
| `GET /api/model-trainer/jobs` | Restore recent runs after a page reload |
| `GET /api/model-trainer/run/{id}` | Progress, losses, saved models and errors |
| `POST /api/model-trainer/run/{id}/cancel` | Request cancellation |
| `GET /api/model-trainer/models` | List this account's saved models and metrics |
| `POST /api/model-trainer/models/{id}/predict` | Forecast using recent completed candles |

Bot create/edit requests use `strategy_name: "AlexNet"` and `ai_model_id`.
The existing authentication and CSRF checks cover all trainer endpoints.

Training requests may include `architecture`; omission preserves the AlexNet
default. `/config` provides a `models` capability catalog with per-family
defaults, supported timeframes, dependency availability and bot compatibility.
Transformer preview responses include `observed_candles` and `forecast_candles`
arrays with UTC opening timestamps and numeric `open`, `high`, `low`, `close`,
and `volume` fields.
