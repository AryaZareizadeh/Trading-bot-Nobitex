# Nobitex API audit — 2026-10-04

This audit traces every outbound Nobitex request in the Python application and checks the repository reference plus official documentation. Findings below describe the code at the start of this investigation; remediation is tracked in the accompanying code changes. No account credentials were inspected, and no account, order, transfer, or cancellation requests were sent to the exchange. A production incident has not been reproduced from exchange logs.

## Changes implemented

- Read-only calls retry temporary transport/server failures up to three attempts, including the POST order-status lookup. Mutation requests (open, close, cancel, transfer) are sent once. Connect/read timeouts are now separate: 5s/15s for reads and 5s/30s for mutations.
- Structured errors are decoded before HTTP errors discard their exchange code. HTTP/JSON rate limits preserve the documented delay; clients share cooldowns and rolling endpoint budgets within this Python process, including the conservative 30/10min position-list limit. Short read cooldowns may wait; mutation requests reject locally immediately while throttled, avoiding queued submissions after a bot stops. Separate processes and other applications are outside this local budget.
- Polling tolerates temporary read failures within its existing fill deadline. Fifteen-second checks reduce position-status pressure, later partial fills query the owned position directly, and terminal orders awaiting position visibility/settlement are not canceled again. A terminal opening order with zero fill reports failure. Partial-fill repricing preserves an already-requested exit.
- Documented rejection codes release the rejected intent's market reservation and report the exchange reason. Unknown errors, HTTP 5xx, duplicate-order errors, and lost submission responses remain uncertain; no order is automatically reposted. Existing historical uncertain intents are not silently reclassified.
- Running real bots with unresolved intents attempt reconciliation every 30s while awaiting their next candle. These checks do not evaluate stale signals or submit new orders. Successful reconciliation clears stale exchange errors; failures generate durable warning events.
- Opening orders use a validated current quote for sizing and price, and do not fall back to an old candle when the quote fails. Account preflight/network latency and last-trade versus bid/ask differences can still affect the bounded fill. Active-order dashboard reads now request details and follow all pages. Endpoint/method/duration/failure-code logging helps identify the next actual failure without logging authentication headers.

The existing fill deadlines are preserved; they are not HTTP request timeouts. Failures before an intent is prepared still defer signal execution until the ordinary strategy wake. A lost opening response whose completed order cannot be found by active-only client-ID lookup still requires binding the verified exchange order through the existing reconciliation workflow. Restart the dashboard/server to load these code changes; this audit did not stop or restart live bots.

## Failures that can explain the reported pause or timeout

1. **One failed status read interrupts an otherwise accepted order.** `OrderExecutor.poll()` originally let any exception from `refresh()` escape. A timeout, HTTP 429, or temporary server error after successful placement therefore immediately ended polling. `_sync_exchange()` saved a reconciliation error while the running bot then waited for its next candle. That could postpone another check for minutes, hours, or a day. The durable reservation correctly prevented another order, but looked like a bot that had stopped opening positions.
2. **Some definite rejection responses were stored as uncertain outcomes.** `submit()` originally recognized only `_FATAL_ORDER_ERRORS` as rejection. Documented price, format, verification, market, and settlement errors outside that set reserved the market indefinitely. For opening orders, recovery by `clientOrderId` cannot find a request that was never accepted. Error codes and missing-result handling need separate treatment from an ambiguous network outcome.
3. **Opening orders used the last completed candle's price.** `_place_single_order()` originally used `self.df.Close.iloc[-1]` for both quantity and the market order's price bound. A price move while evaluating signals or models could make the bound stale. Market execution is bounded; insufficient liquidity within the permitted price band can cancel the order even after acceptance. A candle price of 100 and current offers above 101 illustrates why a market buy may fail to fill. Closing already attempted a current quote, although it silently fell back to the candle price if that read failed. [Official order behavior](https://github.com/nobitex/docs-api/blob/master/source/includes/_market_trade.md#%D9%86%DA%A9%D8%A7%D8%AA-%D9%88-%D9%85%D9%84%D8%A7%D8%AD%D8%B8%D8%A7%D8%AA)
4. **Calls from multiple bots have no combined request budget in the original client.** Polling an opening order after partial fills calls the positions list every five seconds; closing polls a single position every five seconds. Position status is limited to 100 requests per ten minutes, so one persistent ten-minute close can make approximately 120 calls before other consumers are counted. The current portal specifies a stricter positions-list budget than the local snapshot; see the table below. A successful read retry alone cannot prevent an account-wide rate-limit problem. [Position status](https://apidocs.nobitex.ir/margin_trade/مشاهده-یک-موقعیت), [positions list](https://apidocs.nobitex.ir/margin_trade/مشاهده-لیست-موقعیت-ها)
5. **The original client discarded exchange error details on non-2xx responses.** `_call()` called `raise_for_status()` before reading JSON. Nobitex's `code`, `backOff`, and `limit` therefore did not reach the trading error classifier. The documented wait is `backOff` seconds; repeated aggressive retries can block the token across all endpoints for two minutes. Endpoint, HTTP status, and request duration were also absent from the durable failure explanation. [Official rate-limit rules](https://github.com/nobitex/docs-api/blob/master/source/includes/_general_notes.md#%D9%85%D8%AD%D8%AF%D9%88%D8%AF%DB%8C%D8%AA-%D9%81%D8%B1%D8%A7%D8%AE%D9%88%D8%A7%D9%86%DB%8C)

These are observable code paths, not proof that any particular one caused the user's production symptom. A captured timeout, request diagnostic, and corresponding durable intent are needed to establish that.

## Authentication and response contracts

Ed25519 signing matches the current official guide: current Unix seconds, uppercase method, full path including query string, and the exact compact JSON body that is subsequently sent. URL-safe Base64 is correct. The production timestamp must be within 30 seconds of the server; this audit did not inspect the machine's actual offset. Token fallback uses the documented `Authorization: Token ...` header. Explicit testnet selection is implemented. [API-key guide](https://apidocs.nobitex.ir/api_key/api-key-guide)

Business errors may be returned with HTTP 200. The original `_call()` correctly checked body `status` after successful HTTP handling, but did not validate the top-level JSON shape before calling `.get()` and did not preserve errors from non-2xx bodies. An HTML gateway error or malformed body is a transport/protocol failure, not evidence that a money-changing request was rejected.

The current portal is internally inconsistent about positions list/status scopes: endpoint pages state `TRADE`, while the guide maps those reads to `READ`. Existing `READ,TRADE` trading keys meet both descriptions; read-only monitoring keys deserve an explicit compatibility check. `margin/markets/list` is now described as public with optional personalized authentication.

At the initial audit, network routing differed: `NobitexClient` disabled inherited proxies and accepted `NOBITEX_HTTPS_PROXY`; candle and display-quote sessions disabled inherited proxies without applying that override; public spot requests originally retained Requests' default environment behavior. On 2026-10-06, the user's requested direct-only policy replaced these routes with consistent proxy bypass for all Nobitex requests, including the help article. Other exchanges use the configured proxy. See [the deployed routing and connection checks](nobitex-connectivity.md). Public research/candle URLs remain production even when the authenticated client selects testnet.

## Definite rejection versus uncertain acceptance

The official margin source documents `status=failed` responses as nonacceptance. The original rejection set omitted these errors: `FeatureUnavailable`, `ParseError`, `TradeLimitation`, `InvalidMarketPair`, `BadPrice`, and `PriceConditionFailed`; close additionally omits `NoOpenPosition`, `ExceedLiability`, and `ExceedTotalAsset`. Existing recognized errors include balance, minimum size, pool capacity, leverage, disabled trading/market, unsupported currency, and `ExceedDlegationLimit` (the documented misspelling). [Margin error tables](https://github.com/nobitex/docs-api/blob/master/source/includes/_position.md)

`DuplicateOrder` and `DuplicateClientOrderId` indicate that a related earlier order may exist. Even when the latest request was rejected, that signal does not establish that no prior position exists. Similarly, a timeout, lost response, malformed response, unexpected 5xx, or missing active-only client-ID lookup must retain the durable unresolved intent. Automatic money-changing retries would risk creating another position.

## Timing and remaining contract cautions

| Operation | Original timing / implication |
|---|---|
| Single client HTTP call | Requests `timeout=15`; this bounds socket waits, not total elapsed duration of a multi-call workflow. [Requests timeout semantics](https://requests.readthedocs.io/en/latest/user/quickstart/#timeouts) |
| Opening fill deadline | 5min for 1–30min candles; 30min for 1–4h; 90min for daily. This is an application fill/reconciliation deadline, distinct from HTTP timeout. |
| Closing fill deadline | 2min for 1–30min; 5min for 1–4h; 10min for daily. The durable executor reconciles at five-second intervals. |
| Initial candle fetch | Up to ten outer attempts, exponential sleep capped at 30s; a history attempt may contain multiple HTTP pages. |
| Exchange dashboard refresh | Every 120s in code, despite comments/reference text mentioning 30s. Uses position list and active-order list. |
| Portfolio snapshot | Hourly background job; an explicit portfolio view/snapshot also triggers balances, position list, and per-currency quote reads. |
| Unresolved live order | Original bot retried only at ordinary candle/expiry wakes. Recovery must be scheduled independently while preserving reservation and ownership. |

Quantity sizing originally rounded to six decimals for every market rather than applying live per-market `amountPrecisions`. Rounding a delegation cap upward can slightly exceed the allowed limit; exchange-side amount rounding can also leave the local intended amount different from the accepted amount. `_format_price()` uses fixed price bands rather than `pricePrecisions`. These can explain precision/minimum-size rejections for particular markets, but no failing market payload was observed. The close amount also converts decimal liability strings to float before formatting ten decimals; exact decimal subtraction is preferable for final settlement.

`_fetch_delegation_limit()` originally continued with the full amount after any limit-read error. That can turn a read-rate-limit/network failure into a placement rejection. A fresh margin balance read is used on the actual `_sync_exchange()` opening path; the legacy 30-minute wallet-cache helper is not called there.

`active_orders()` originally lacks pagination despite saying it fetches all orders. The documented default is 100, so this is a definite completeness limitation for accounts with more open orders. It should not be presented as the primary explanation for a small account's order-placement timeout.

## Verification needed for remediation

Offline tests should cover transient read failures after accepted placement; honoring HTTP/JSON backoff; preserving money-changing uncertainty without reposting; handling known rejection codes; reconciling terminal canceled/partial orders; and recovering unresolved intents between candles. Signing tests should compare the transmitted prepared path/body with the bytes signed, and pagination tests should check more than one active-order page.

Public official documentation was checked without logging into the exchange. The repository's browse executable could not launch because its Chromium runtime was absent; read-only web retrieval was used as a fallback. Some migrated documentation pages, including order status and public market-data pages, timed out during retrieval; current official GitHub source was used for those sections. Live account reachability, effective rate limits, permission validity, clock offset, and the user's original production error remain unverified.
